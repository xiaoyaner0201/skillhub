## 1. Source Contract 分层

### 原始事实（FACT）

- 上游维护者要求：订阅创建前检查当前 metadata 读权；published/yanked fan-out 在事件处理
  时按当前规则过滤；复用 `VisibilityChecker` 或共享 policy；补 EN/zh 文案和 private、
  namespace-only、hidden、removed-member、disabled-user 五类场景的两路径测试。
- base 上 `SkillSubscriptionService.subscribe` 只检查 skill 存在；`unsubscribe` 与
  `isSubscribed` 同样只检查存在。subscribe 的拒绝面、账号状态和 namespace membership
  均不存在。
- base 上 published/yanked 两个 subscriber listener 对订阅者无条件 dispatch，仅分别跳过
  publisher/actor；最终 sink 是 `NotificationService.create` 的 recipient-specific row 与
  `SseEmitterManager.push`。
- `VisibilityChecker` 现有两个 interface 已表达 hidden、`latestVersionId == null`、PUBLIC /
  NAMESPACE_ONLY / PRIVATE、owner/admin/namespace-owner 和 `SUPER_ADMIN`。production 调用点
  共 8 处：`SkillQueryService` 三处、`SkillDownloadService`、`SkillTagService`、
  `SkillLabelAppService`、`CompatSkillLookupService`、`SecurityAuditController`。
- r2 的 `SubscriptionMetadataAccessPolicy` 与 `SubscriptionRecipientEligibility` 是维护者点名
  反对的 parallel model；它们不是本计划的移植来源。
- inventory 为 D2 direct Java AST/call-site enumeration，但明确不能证明 Spring runtime
  listener/proxy/transaction/async、reflection、generated code、external module 与 runtime
  conditional registration 的完整性。

### 明确要求（REQUIREMENT）

- subscribe 对 metadata 不可读的当前用户抛 `DomainForbiddenException`；拒绝必须发生在
  subscription row、counter 与 `SkillSubscribedEvent` 之前。
- fan-out 必须使用事件处理时的实时 account、namespace member 与 platform role；账号与成员
  关系必须批量读取，fan-out loop 内不得逐用户查库。
- 可见性判定唯一落在 `VisibilityChecker`。任何新 resolver 只能批量装配事实并调用 checker，
  不得自行判断 visibility、hidden、latest version、namespace status、account status 或 role。
- publisher/actor skip、notification preference、row persistence、SSE payload 与 SSE failure
  非关键语义保持不变；资格事实读取失败时必须在任何 recipient sink 前 fail closed。
- 五类场景 × subscribe/fan-out 两条路径共十组具名断言必须落在具体测试文件；EN/zh 必须通过
  真实 `MessageSource` 读出，不能回落裸 code。
- HIGH_RISK 验收绑定 exact tree；QA 采用 independent charter ∪ Plan probes ∪ regression，
  Reviewer/Council 不能把本 inventory 当作完整性上界。

### 合理推导（INFERENCE）

- 新增一个 `VisibilityChecker` full-context overload，比把账号/namespace 条件留在 resolver
  更符合「一个 policy source」：账号 active、namespace archived 与 platform role 的优先级
  都在 checker 内，resolver 没有第二套决策树。
- 现有两个 overload 保持源码与行为兼容；8 个既有 consumer 不迁移到 full-context overload。
  这样 R3 的收敛不会无意改变 download、tag、label、compat 或 security audit 的既有授权面，
  但它们必须作为显式 regression path 被执行。
- subscribe 是单一 actor，不存在 fan-out N+1；可在 service 中加载一个 account、namespace 与
  membership，再调用同一个 full-context checker。fan-out 另用批量 resolver。
- active `SUPER_ADMIN` 按 checker 既有语义放行 hidden/private/unpublished，并可越过 archived
  non-member gate；disabled/missing account 即使带 `SUPER_ADMIN` 仍拒绝。该优先级必须由
  checker 测试固定，不能散落在 caller。
- yank 使用事件处理时 skill 的当前 `latestVersionId`。若 yank 最后一个 published version 后
  `latestVersionId == null`，仍沿 checker 的 owner-only 规则；不得重新引入 `wasPublished`
  字段或历史可见性旁路。

## 4. R1：unsubscribe / isSubscribed 与存量关系选择题

- `unsubscribe`：冻结为不加 current-read gate。用户即使因 PRIVATE、hidden、removed-member、
  disabled 后恢复登录等状态失去 read access，仍可删除自己的存量 row；这是撤权后的退出
  路径，不能被 subscribe 的新门禁反向锁死。
- `isSubscribed`：本计划明确要求 Coder 保持现有 own-relation boolean 语义，不临场跟随
  subscribe 收紧。理由是响应只暴露 caller 自己对其已知 `skillId` 的关系，不含 skill
  metadata；改变为 403/false 会破坏 unsubscribe UI/兼容语义，且不解决已登记的
  `/me/subscriptions` read-model 遗留问题。

但存量 row 的长期产品语义未获上游批准，必须在公开草稿中交回维护者选择，不能把本计划
写成“maintainer 已批准”：

1. **A（本计划的非破坏性实现基线，推荐）**：保留 row；fan-out 每次按当前读权过滤；
   `unsubscribe` 与 `isSubscribed` 保持上述语义。
2. **B**：保留 row，但 `isSubscribed` 也按当前读权返回 false/403；需维护者指定 masking 与
   UI 行为后另出 plan revision。
3. **C**：清理/迁移无权 row 并修正 count；明确超出本任务 non-goal，需独立 migration 方案。

Plan Gate 的内部批准只冻结 A 为当前代码基线，不得在 PR 文案中冒充上游对长期数据策略的
裁定；若维护者在 Publication 阶段选择 B/C，先回 Planner，不能由 Coder顺手实现。

## 5. 方案比较与冻结选择

### A（冻结）：`VisibilityChecker` full-context overload + 无策略批量 resolver

在 checker 内集中 account/namespace/role 优先级；subscribe 单 actor 装配事实后调用；fan-out
resolver 只批量装配并逐个调用。现有 overload 与 8 consumer 保持兼容。

优点：唯一授权 source、fan-out 无 N+1、R1/R2 同一判定、差异可被 checker 单测完整固定；
不扩大 8 个现役 caller 的运行时依赖。代价：checker 多一个 interface，需要清晰命名和
优先级测试。

### B：把 8 个 consumer 全量迁移到账号/namespace full context

语义表面更统一，但需要每条 query/download/tag/label/compat/audit path 增加 account 与
namespace 装配，造成显著 N+1/接口/错误 masking 风险，超出维护者要求。拒绝。

### C：移植 r2 的两类 subscription policy

实现较快，但 duplicate hidden/private/latest/archived 规则，且漏 `SUPER_ADMIN`，正是
维护者拒绝的 parallel model。拒绝；两个类不得出现在 candidate diff。

## 11. Falsification / RETURN 条件

任一成立即证明 plan-r1 不完整，必须停止实现并回 Planner：

- 新 resolver 出现任一独立 visibility/account/namespace/role 决策分支；或 r2 两个 parallel
  类出现在 diff。
- existing `VisibilityChecker` overload 行为或 8 consumer observable result 发生变化。
- disabled user、removed member、private/hidden ordinary member 任一到达 row 或 SSE；合法
  namespace member 被误伤。
- fan-out loop 内出现 account/member/platform-role repository call，或 batch 失败后已有部分
  recipient sink。
- yank 为绕过 latest-null 引入 `wasPublished` 或修改 event record/producer。
- Spring runtime probe显示 rollback 仍 dispatch、listener 非 AFTER_COMMIT、或 async proxy 未
  生效；且无法以本写集内修复。
- candidate scan发现新的 consumer/sink/reflection/generated path，或 blind Reviewer 找到
  inventory 外 material path。
- 非 ledger diff 含 `confirmPublish`、`SkillReviewSubmitService`、migration、workflow、
  `RecipientResolver` 或其它禁止路径。
- 上游对存量 `isSubscribed`/row 选择 B/C；须先出 plan-r2，不能把选择题当作已批准。
