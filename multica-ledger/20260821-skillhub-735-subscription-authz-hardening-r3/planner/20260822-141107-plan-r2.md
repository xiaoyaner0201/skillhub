## 1. `R-P1-01`：重建 latest-null 语义

### 1.1 裁决

撤销 plan-r1 的 `LATEST_VERSION_RULE_UNCHANGED` 与 state
`yanked-latest-null-denied`。替换为具名 invariant：

`YANK_REVOCATION_NOTICE_REACHABILITY`

> 对一条真实 `SkillVersionYankedEvent`，若本次 yank 同一事务把
> `skill.latestVersionId` 清为 `null`，不得仅因该自致状态而吞掉撤回通知。通知资格仍使用
> 处理时的账号、namespace、membership、visibility、hidden 与平台角色事实；actor 仍跳过。

理由：撤回通知的收件人正是可能已安装被撤版本的人；以本次撤回造成的 latest-null 再否定
本次撤回消息，是过滤器自我否定。base 对订阅者无条件 dispatch，r1 candidate 把普通 PUBLIC
订阅者由有通知改成零 sink，因此无论最终维护者是否接受，这都是必须在 PR 正文披露的存量行为
变化。Planner 不以一条符合旧计划的绿测试证明旧计划正确，现据反例重建。

### 1.2 checker interface 与优先级

在 `VisibilityChecker` 定义显式 access purpose（名称可按仓库风格调整，但只能表达以下两种
语义）：

- `METADATA_READ`：旧两个 overload、subscribe、published fan-out 的默认目的；原
  `latestVersionId == null` owner-only 规则不变。
- `YANK_REVOCATION_NOTICE`：仅 yanked subscriber listener 使用。它只豁免
  `latestVersionId == null` 这一 publication-state guard，再按当前 `hidden` 与
  PUBLIC / NAMESPACE_ONLY / PRIVATE 规则判定；账号 missing/disabled、namespace archived、
  current membership、平台角色通道政策以及 actor skip 均不被豁免。

full-context overload 必须接收 purpose；旧 overload 委托 `METADATA_READ`。published listener
传 `METADATA_READ`，yanked listener 传 `YANK_REVOCATION_NOTICE`。不得把 purpose 藏在 boolean
参数里，不新增 `wasPublished`、历史 snapshot、event record 字段或 producer 改动。

purpose 的例外必须落在 `VisibilityChecker` 内。`SubscriberAccessResolver` 仅接收并原样转发
purpose；不得出现 `event instanceof`、`latestVersionId == null`、visibility、account status、
namespace status 或 role allow/deny 分支。listener 选择与其具名 event method 对应的 purpose
属于编排，不属于第二套授权判定。

## 2. `executor-probe-spec`：以真实 `CallerRunsPolicy` 重建 invariant

### 2.1 撤销不可能的 rejection 规格

撤销 plan-r1 probe `runtime-executor-rejection-zero-sink` 及
`FAIL_CLOSED_BEFORE_SINK` 中“async admission failure 必为零 sink”的泛化。生产
`AsyncConfig.skillhubEventExecutor` 在 core=2、max=4、queue=100 后使用
`ThreadPoolExecutor.CallerRunsPolicy`；executor 尚在运行但池与队列饱和时，任务不被丢弃，
而是在提交线程同步执行。用手写 rejecting lambda 得到零 row 测的是另一个对象，不能作为
本仓库配置的证据。

替换为具名 invariant：

`AFTER_COMMIT_CALLER_RUNS_DELIVERY`

> 正常容量时，subscriber listener 只在源事务 commit 后经已注册的 Spring transaction-event
> proxy 与 `skillhubEventExecutor` 异步执行；rollback 或无活动事务发布时为零 sink。配置的
> executor 饱和时，同一 listener 在提交/发布线程同步执行并阻塞该线程直至 fan-out 完成，
> 但仍处于 source commit 之后，且 Notification row 与 SSE 的 tuple/数量必须与 ordinary async
> 路径一致。

`ASYNC_AFTER_COMMIT` 因而拆成以下可独立证伪的三条：

- `AFTER_COMMIT_ASYNC_DELIVERY`：有容量时 source commit 之前 0 sink，commit 后在
  `skillhub-event-*` thread 获得 exact row + SSE。
- `ROLLBACK_AND_NO_TX_ZERO_SINK`：真实 rollback 与无活动 transaction 发布均 0 row / 0 SSE；
  resolver/dispatcher 也不被调用。
- `AFTER_COMMIT_CALLER_RUNS_DELIVERY`：真实配置饱和后在 publisher/commit thread 同步完成；
  该 thread 被 sink 人为阻塞期间 commit future 不完成，释放后 exact row + SSE 均可读。

executor 已 shutdown 时 `CallerRunsPolicy` 的行为不纳入本改动的 delivery guarantee；该状态是
应用生命周期停止边界，保留为 PR 残留风险，不得用 shutdown 来伪造本节饱和 probe。

### 2.2 新事务与 row-before-SSE 口径

Spring `afterCommit` 回调执行时原 transaction 资源尚可能绑定；普通 `REQUIRED` 写入可能加入一笔
已提交但尚未 cleanup 的 transaction，造成保存不再被 commit。仓库已有
`PostgresFullTextIndexService.index` 的 `REQUIRES_NEW` 先例和
`LabelSearchSyncIntegrationTest.syncRebuildInAfterCommitPhase_persistsIndex` 反例测试。

本计划授权且仅授权把
`server/skillhub-notification/src/main/java/com/iflytek/skillhub/notification/service/NotificationService.java`
的 `create(...)` transaction propagation 改为 `REQUIRES_NEW`：

1. normal async thread 无 ambient transaction 时开启并提交一笔物理 transaction；
2. CallerRuns 位于 source `afterCommit` 时 suspend 残余 source transaction，开启并提交新 transaction；
3. `create(...)` 返回后 `NotificationDispatcher` 才调用 `SseEmitterManager.push`，所以 row commit
   先于 SSE；SSE failure 继续 non-critical，不回滚已经提交的 row；
4. 不给整个 listener/fan-out loop 套外层 transaction，避免 SSE 早于 row commit；不改
   `NotificationDispatcher` payload/preference/error contract。

`NotificationService.create` 的生产 caller 仅为 `NotificationDispatcher`，而 dispatcher 的生产
调用均来自同一 registered transaction listener；尽管如此，propagation 改动覆盖所有通知类别，
故必须运行 `NotificationServiceTest`、`NotificationDispatcherTest` 以及至少一条非 subscriber
event listener runtime regression。若新证据显示有未枚举的 transaction 内 caller 依赖外层
rollback，本计划被证伪并回 Planner，Coder 不得继续扩大修复。

### 2.3 三个真实 Spring probes

下列 probe 均落在
`server/skillhub-app/src/test/java/com/iflytek/skillhub/listener/SubscriberNotificationRuntimeIntegrationTest.java`，
使用 `@SpringBootTest`、真实 `ApplicationEventPublisher`、真实 transaction manager、registered

真实 `NotificationDispatcher` 与真实 `SseEmitterManager`。禁止 `@MockBean` / Mockito 替代上述

   - 在 transaction 内发布具备真实 namespace/skill/subscription/account/membership/RBAC fixture

## 8. Council nomination（r2）

### Martin Kleppmann-style — derived-record / delivery ordering

适配理由：`spring-runtime-dispatch` 从 source commit 派生 Notification row 与 SSE，且
`AFTER_COMMIT_CALLER_RUNS_DELIVERY` 在 configured executor 饱和时改变执行 thread/阻塞形态；
这比抽象的 annotation review 更需要逐项核对 durable derived record 与 transport order。

must answer：

1. ordinary async 与 CallerRuns 是否都发生在 source commit 后，且 row commit 严格先于 SSE？
2. `NotificationService.create(REQUIRES_NEW)` 在 afterCommit 残余资源绑定时是否真的产生新物理
   transaction，而非仅 flush 到已结束 transaction？
3. 饱和 probe 是否占满真实 bean 的 workers/queue，并证明 publisher thread 阻塞到 fan-out 完成？
4. rollback/no-tx 是否通过已注册 proxy 产生严格零 sink，而不是测试根本没有注册 listener？

### Bruce Schneier-style — dissent / unsolicited disclosure

适配理由：`yanked-subscriber-fanout` 的
`YANK_REVOCATION_NOTICE_REACHABILITY` 有意放宽 self-invalidating latest-null guard，同时
`PRIVATE_METADATA_CONFIDENTIALITY` 与 `R-P1-07` 决定 active SUPER_ADMIN 是否得到未经请求的
portal push；这是本轮最需要反对者构造滥用反例的边界。该 lens 为 dissent role。

must answer：

1. YANK purpose 能否被 published/subscribe/任意非 yank caller 伪用而扩大 ordinary metadata read？
2. latest-null 豁免后，private/hidden/removed/disabled 任一状态是否能到 row 或 SSE？
3. `R-P1-07` A/B 的通道后果是否完整呈现，是否有文字暗示 SUPER_ADMIN push 已获维护者同意？
4. resolver/RBAC assembly 中是否仍存在 checker 外 allow/deny、角色降级或 fail-open？

### Kent Beck-style — executable falsification

适配理由：`subscription-create`、两条 fan-out 与 `visibility-checker-consumer-regression` 需以
`RECIPIENT_ORDER_PRESERVED_TO_SINK`、reachable RED commits 和 base/candidate matrix 杀死错误实现，
QA r1 已证明 mock/annotation 绿不能替代 final-sink 证据。

must answer：

1. `RED_BASE_SHA` / `RED_DELTA_SHA` 能否 checkout、compile，并以目标断言失败而非 scaffolding error？
2. real runtime test 是否穿过 publisher→transaction proxy→configured executor→real row/SSE，且
   未 stub persistence/transport？
3. listener `InOrder` 与 DB/SSE 实际顺序能否杀死“resolver 保序但 final loop 重排”的 mutant？
4. legacy matrix 是否在 base 与 candidate 运行同一 case ids 并 byte-identical，而非两个各自绿 suite？
5. account/membership/platform-role/namespace 四类 failure 是否在 published/yanked 两路都得到
   final 0 row/0 SSE？

declined lenses：Leslie Lamport-style 本轮不另占席位，因为具体的 afterCommit-derived row、
CallerRuns 与 transport order 已由 Kleppmann-style 聚焦；Linus Torvalds-style 不另占席位，因为
接口增长被单一 access-purpose 与单一 RBAC batch seam 限定，本轮更关键的是可执行证伪而非
通用 API 风格。
