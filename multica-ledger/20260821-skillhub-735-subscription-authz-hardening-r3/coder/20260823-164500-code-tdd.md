## 五、执行事故与自陈更正（两项）

### 5.1 `SubscriberNotificationRuntimeIntegrationTest` 挂死 47 分钟

首轮 GREEN 跑在该类上挂死（非变慢）。jstack 定位（`coder/logs/20260823-152500-hang-jstack.txt`）：main thread 停在 `saturateConfiguredExecutor` 的 filler 任务体内，与 4 条 `skillhub-event-*` 一起 park 在同一个 `CountDownLatch`——即饱和 helper 提交超量，`CallerRunsPolicy` 把一个 filler 交回给了饱和线程本人，而该 latch 只有它能 countDown，自锁。

根因是 helper 里「先算固定条数再提交」的算法本身不收敛：能吸收多少 filler 取决于上一条测试留下多少存活 worker（`ThreadPoolTaskExecutor` keepAlive 默认 60s），且每有一个 worker 被唤醒就又空出一个队列槽；`ThreadPoolExecutor` 只在 offer 失败时才扩容到 core 之上。改为：提交到池子自报饱和为止；被 `CallerRunsPolicy` 交回饱和线程的 filler 立即返回（拿到它本身就证明池满）；失败路径先 `release.countDown()` 再抛，避免一条真失败被后续每个 `awaitExecutorIdle` 的级联淹没（实测级联 7 → 1）。

**这是测试脚手架的修复，不是为了让 probe 变绿去动 executor**：production `AsyncConfig` 的 core/max/queue/policy 一行未改，且由 `springRegistry_reportsSubscriberProxyPhaseExecutorAndAllListeners` 在同一轮里读回断言 core=2 / max=4 / queue=100 / `CallerRunsPolicy`。饱和后的关键断言（`blocked.threadId()` 等于 publisher thread id、`future.isDone()` 为 false）保持不变且通过。诊断过程两次中间态原始输出：`coder/logs/20260823-155500-saturation-diag-a.log`、`-160500-saturation-diag-b.log`。**请 QA 重点复核这一处脚手架改动是否削弱了 probe 的区分力。**
