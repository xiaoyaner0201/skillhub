## 1. Source Contract 分层与关键裁决

### FACT

- Maintainer XiaoSeS 的四项裁定是：订阅创建检查当前 metadata 读权；published/yanked
  subscriber fanout 在处理时按当前读权过滤；复用 `VisibilityChecker` 或共享访问策略；补
  EN/zh 文案与 private、namespace-only、hidden、removed-member、disabled-user 测试。
- base 上 `SkillSubscriptionService.subscribe` 只检查 skill 是否存在，之后就可能写 row、增加
  count、发布事件；两个 subscriber listener 只跳过 publisher/actor，未做当前读权过滤。
- base 上 `VisibilityChecker` 已规定 PRIVATE 为 owner 或 namespace ADMIN/OWNER，hidden 同样
  owner/manager，NAMESPACE_ONLY 为当前 member，`SUPER_ADMIN` 可访问。它有 8 个 production
  call sites。
- `SubscriptionMetadataAccessPolicy` 在 base 与 r3 均不存在，只存在于 PR #735 head。因此 Issue
  所称“既有语义”只能是要求保留 #735 head 表达的 PRIVATE `owner || manager` 结果，而不是要求
  把该平行类带回 base。
- `GET /me/subscriptions` 当前从持久 row 直接组装 `SkillSummaryResponse`，没有 `VisibilityChecker`
  过滤；权限收紧后的 stale row 会继续暴露 id、slug、displayName、summary、visibility、namespace
  和 lifecycle 字段。
- D2 inventory 静态枚举 14 个 candidate，但无法单独证明 Spring proxy/transaction/executor、
  reflection/generated/external/runtime-conditional 路径完整。

### REQUIREMENT

- subscribe 的拒绝必须在 row、count、event 三个 sink 之前；错误 code 为
  `error.skill.subscription.noPermission`，EN/zh 均须真实解析。
- fanout 以事件处理时的 current account、namespace membership、platform RBAC 为事实源；任何
  authority load failure 均须在第一个 recipient sink 前 fail closed。
- `VisibilityChecker` 是唯一授权判定点。新的 resolver 只能批量装配 facts、保持输入顺序并调用
  checker；不得复制 visibility/hidden/latest/account/namespace/role 决策树。
- PRIVATE manager 仍允许；active `SUPER_ADMIN` 仍沿 checker 既有规则允许；disabled/missing
  account 即使携带角色也必须拒绝。
- stale `/me/subscriptions` row 不得继续暴露当前不可读 metadata。由于 migration/prune 明确是
  non-goal，本次在读时过滤，不删除 row、不修 count。
- unsubscribe 保持撤权逃生路径；`isSubscribed` 保持 authenticated caller 的 own-row boolean，
  anonymous 保持 false。二者不携带 metadata，不能被 subscribe 新门禁反向锁死。

### INFERENCE

- 在 `VisibilityChecker` 加 full-context overload，可把 account active、namespace archived、current
  namespace role、platform roles 都收敛到同一 policy；旧 overload 原样保留，8 个既有 consumer
  不迁移。
- fanout 用批量 `SubscriberAccessResolver`；subscribe 与 `/me/subscriptions` 是单 actor/单 page，
  可装配当前 facts 后调用同一 checker。`/me/subscriptions` 必须先对 page 中 skill 做 current-read
  过滤，再组装 response；返回 `total` 必须与过滤后的可见集合一致，不能泄露 stale row 数量。
- yank notice 不能仅因该 yank 清空 `latestVersionId` 而被自我抑制，因此 checker 需要窄化的
  `YANK_REVOCATION_NOTICE` purpose；它只能跳过 latest-null publication-state guard，不能跳过
  private/hidden/membership/account/namespace gate。
- `NotificationService.create` 使用 `REQUIRES_NEW`，以保证 AFTER_COMMIT + CallerRuns 路径的 row
  真正提交后再 SSE；这属于现有 fanout sink 的事务正确性，不是扩大通知范围。

### ASSUMPTION（可证伪）

- EN/zh 文案分别冻结为 `You do not have permission to subscribe to this skill` / `你没有权限订阅该技能`。
- authenticated principal 的 `platformRoles()` 是 subscribe 当次平台角色输入；fanout 和 stale read
  则从持久 RBAC 重新读取。若仓库有更高阶权威契约与此冲突，Coder 报 `PLAN_GAP`。
- `@TransactionalEventListener` 默认 phase 为 AFTER_COMMIT，且无事务时不 fallback；若 runtime
  probe 读回不同，Plan 被证伪。
- 对 `/me/subscriptions` 采用“visible-result pagination”语义：可读 row 组成结果集，`total/page/size`
  均针对该集合；若只能 page 后过滤而导致 short page 或 total 泄露，视为实现缺陷。

### NON-GOAL

- 不做 migration、prune、历史 row 清理、subscription count repair。
- 不改变 `SubscriptionMetadataAccessPolicy`（不创建该类）；不改 8 个旧 `VisibilityChecker` caller
  的 production code，不改变 PRIVATE `owner || manager`。
- 不改 `confirmPublish`、event producer/record、search implementation、notification payload、
  preference contract、前端、workflow 或公开 PR；Publication 另行处理。

### 边界对象缺席的裁决

Issue 的“保持 `SubscriptionMetadataAccessPolicy` 既有语义”与 maintainer 第 3 项可以同时满足：
**不带回该 base 缺席的平行 class**，而在已有 `VisibilityChecker` 的 full-context overload 中固定
同一 PRIVATE `owner || manager` 结果。这里没有必须二选一的 `PLAN_GAP`。

## 3. 方案比较

### A（冻结）`VisibilityChecker` full-context + fact-only resolver + stale read-time filtering

授权规则只在 checker；subscribe 单 actor装配 facts；fanout resolver 批量装配；
`/me/subscriptions` 按当前读权过滤但保留 row。优点是同时满足四项裁定、PRIVATE manager 边界、
stale-row confidentiality 与 no-migration non-goal；旧 caller 兼容面可单独做差分。

### B 移植 PR #735 的 `SubscriptionMetadataAccessPolicy`

实现直接，但会形成 maintainer 明确拒绝的平行 visibility model，且 base 无此契约。拒绝。

### C 只在 subscribe/fanout 加 gate，stale read 维持原状

字面贴四项，但 inventory 已证明 `/me/subscriptions` 是 recipient-visible metadata sink；权限回收后
继续泄露违反仓库隐私/隔离不变量。拒绝。

### D 清理/迁移 stale row

可消除历史记录，但直接违反 no migration/prune/cleanup 边界，并引入 count 修复与事务设计。
拒绝。

## 10. Falsification conditions

任一项出现即 Plan 不完整，Coder 必须停并报 `PLAN_GAP`：

- repository 更高阶契约证明 PRIVATE 并非 owner||manager，或 principal roles 不是 subscribe 权威输入；
- stale row 无法在不做 migration/prune 的前提下得到不泄露 total 的可执行 pagination；
- resolver 需要自行判断 visibility/account/role，或 checker 的旧 overload observable 发生变化；
- genuine yank 的 latest-null 状态无法与普通 unpublished read 用窄化 purpose 区分；
- Spring runtime readback表明 listener 非 AFTER_COMMIT、no-tx fallback、或 row 无法独立提交后再 SSE；
- search consumer 会被 subscriber listener 的异常/顺序改变；
- exact-tree scan 出现 inventory 未建模的新 caller/consumer/sink。
