# confirmPublish 授权安全的发布事件计划（plan-r2）

本计划 supersede `planner/20260819-104029-plan-r1.md`。相对 r1：保留 producer 的成功/失败事件契约；新增所有 consumer、订阅入口、event-time 授权、通知持久化/SSE 与搜索索引的完整 reachability；把 r1 错列为 non-goal 的 subscriber authorization/privacy 纳入强制范围；扩大 Coder/QA 写集与验证矩阵；publication 仍需新鲜 gate，当前禁止 PR。旧 r1 与旧 PASS 只保留为历史证据。

## 1. Source Contract：事实、要求、推导、假设、non-goals

### 原始事实与明确要求

- 上游问题要求 `confirmPublish` 成功后产生既有 `SkillPublishedEvent(skillId, versionId, publisherId)`；当前候选提交已在两次 save 后发布，失败时不发布。
- superseding finding 要求历史订阅不能替代事件发生时的读取授权；PRIVATE skill 的撤权、降权、离开 namespace、陈旧订阅、混合 fan-out、跨 namespace 与依赖失败必须 fail-closed。
- 必须追踪 `confirmPublish → SkillPublishedEvent → every listener → final sink` 以及订阅 public entry；必须复用 `VisibilityChecker` 的读取合同，不得把 authorization/privacy 排除为 non-goal。
- 当前 subject 为 commit `a8bbd2c58cf0fe6c880608b203929cd04e71f69c`、tree `3d545b45fa5df8b209b3b7eb97932538bf1c1f82`；base `d2403bb5911953b8f53e62c3f0a9edc291363944`。本阶段只规划，不改生产/测试代码。

### Repository Invariants（源码上位事实）

- `VisibilityChecker.canAccess` 是 skill 读取合同：PUBLIC 对所有人；NAMESPACE_ONLY 对当前 namespace member；PRIVATE 仅 owner、namespace ADMIN/OWNER 或 SUPER_ADMIN；hidden 收紧为 owner/admin；未发布仅 owner。
- `SkillSubscriptionService.subscribe` 当前只 `ensureSkillExists`，因此任何已登录用户均可订阅其不可读的 PRIVATE/NAMESPACE_ONLY/hidden/unpublished skill；这是入口授权缺口。
- `NotificationEventListener.onSkillPublishedForSubscribers` 当前仅按 subscription 查询并排除 publisher，不做 event-time access check；payload 含 `skillId/skillName/slug/namespace/version`，随后 `NotificationDispatcher` 可持久化并 SSE 推送，因此陈旧订阅会泄露元数据。
- `@TransactionalEventListener` 默认 AFTER_COMMIT 且 listener 为 async：producer 事务提交后才执行，listener/dispatcher 失败不能回滚发布；notification preference disabled 时无持久化/SSE；持久化成功后 SSE 失败仅告警，通知仍存在。
- 同一事件还到达 publisher notification listener 与 `SearchIndexEventListener`。搜索 rebuild 建索引但 query 层只展示 PUBLIC/NAMESPACE_ONLY、排除 PRIVATE；该 listener 必须回归但不需要 recipient 授权过滤。

### 合理推导与 Plan Hypothesis

- 资格判断必须发生在通知 listener 内、紧邻 `dispatcher.dispatch` 的最终 side-effect seam，并使用事件处理时的 fresh membership/platform-role records；订阅创建时合格不能授权未来通知。
- 为避免每位 subscriber 查询 membership/role 的 N+1，新增 app-layer、批量的 recipient eligibility module：输入 `Skill + candidate userIds`，一次按 skill namespace 批量取 membership、一次批量取 platform role bindings，逐 recipient 构造 `Map<namespaceId, role>`/platform role set 后调用既有 `VisibilityChecker.canAccess`。若现有 repository 缺少 `findByNamespaceIdAndUserIdIn`，在 domain repository 与 infra JPA adapter 增加这一批量 query。
- eligibility 解析或授权依赖抛异常时，整批 subscriber fan-out 为 0（fail-closed），记录不含敏感 payload 的错误；不得 catch 后继续 dispatch，也不得把 unknown 当 MEMBER。
- 订阅入口应在 domain service 的事务内、保存前用相同 `VisibilityChecker` 合同校验 fresh caller roles；controller 将 `PlatformPrincipal.platformRoles` 与 request-filter 的 `userNsRoles` 传入。GET/DELETE 不扩权：GET 仅暴露自己的关系，DELETE 应允许用户清理 stale subscription。

### 待 Coder 首先核验的假设

- `UserRoleBindingRepository.findByUserIdIn` 可批量提供 SUPER_ADMIN；若 app→auth 依赖不存在则 plan seam 不成立（当前 `skillhub-app` 已依赖 auth，源码显示成立）。
- Spring Data 可由 `NamespaceMemberRepository` 新方法派生批量查询；若实体/adapter 结构不允许，改为 app query repository，但不得退化到 per-recipient query。
- 当前业务认为 PRIVATE owner 或 ADMIN/OWNER 可接收；普通 MEMBER 即使在同 namespace 也不可接收。这直接来自 `VisibilityCheckerTest`，若批准的产品合同另有定义则构成 `PLAN_GAP`。

### Non-goals

- 不改事件类型/字段、通知文案、preference 语义、outbox/重试框架、搜索可见性策略、yank fan-out。
- 不自动删除 stale subscription；它可保留为历史关系，但绝不授予通知资格。
- 不创建 PR、不 merge/release、不把 `multica-ledger/**` 带入未来第三方 publication branch。

## 2. 当前行为与 Change Reachability Graph

### Producer/public caller

`POST /api/{v1|web}/skills/{namespace}/{slug}/confirm-publish` → `SkillLifecycleController`（认证 userId + request-time namespace roles）→ `GovernanceWorkflowAppService` → `SkillLifecycleAppService`（slug/version 解引用）→ `SkillReviewSubmitService.confirmPublish`（PRIVATE、UPLOADED/DRAFT、skill/version 归属、owner/admin 权限）→ save version PUBLISHED → save skill latestVersionId → publish event。任一校验/save 抛错：事务回滚、0 event。

### Event 的全部消费者与 sinks

```text
SkillPublishedEvent
├─ NotificationEventListener.onSkillPublished
│  └─ 仅 publisher==skill.owner → NotificationDispatcher
│     └─ preference → notification_repository.save → SSE(recipient-visible)
├─ NotificationEventListener.onSkillPublishedForSubscribers
│  └─ subscriptionRepository.findAllBySkillId → distinct subscribers
│     └─ [R2: fresh batched eligibility + VisibilityChecker]
│        └─ skip publisher → NotificationDispatcher
│           └─ preference → notification_repository.save → SSE(recipient-visible)
└─ SearchIndexEventListener.onSkillPublished
   └─ SearchRebuildService.rebuildBySkill → skill/version/labels reads
      └─ SearchIndexService.index → skill_search_document
         └─ query-time visibility SQL (PRIVATE excluded)
```

新事件使以上三个 listener 都从 `confirmPublish` 可达。subscriber 分支的派生记录是 `Notification(recipientId, PUBLISH, SUBSCRIPTION_NEW_VERSION, bodyJson, SKILL, skillId)`；payload 可见字段为 `skillId/skillName/slug/namespace/version`。搜索派生记录是 skill search document。

### Subscription public entry

`PUT /api/{v1|web}/skills/{skillId}/subscription` → authenticated `SkillSubscriptionController` → `SkillSubscriptionService.subscribe` → skill read → relationship lookup → save subscription → increment counter → event。当前没有 visibility check。R2 后 caller 必须传 fresh namespace/platform roles，在 relationship save 前用 `VisibilityChecker` 拒绝不可读 skill；重复订阅仍幂等但也必须以当前访问合同为准。DELETE 继续允许删除；GET 继续查询自己的关系。

## 4. 方案比较与冻结选择

### 方案 A（推荐）：listener-adjacent 批量 eligibility module + 入口同合同

在 app listener seam 新增一个小接口（建议 `SubscriptionRecipientEligibility.filterEligible(Skill, Collection<String>)`），内部批量读取当前 membership/platform roles并调用 `VisibilityChecker`。listener 只接收过滤后的 IDs 并 dispatch；subscribe 直接用同一 checker 检查当前 caller context。

优点：授权最靠近最终 sink，覆盖任何 producer 和 stale relationship；显式批量 query 避免 N+1；既有 checker 是唯一规则正本；query failure 可自然阻断 fan-out。代价：写集横跨 app/domain/infra/auth-facing adapter，需精确测试 batch driver 参数与最终 dispatch。

### 方案 B：在 subscription repository 查询中用 SQL 直接筛 recipients

以 `findEligibleSubscriberIds(skillId, visibility, namespaceId...)` 一次 join membership/role。

优点：单 SQL、性能直接。缺点：复制 `VisibilityChecker` 对 PUBLIC/PRIVATE/hidden/unpublished/SUPER_ADMIN 的规则，形成第二授权正本；难以通过现有 domain tests证明一致，未来规则漂移风险高。拒绝。

### 方案 C：订阅创建时校验后永远信任 subscription

改动最小，但撤权/降权/移除后 subscription 立即陈旧，正是已确认 finding；拒绝。

冻结 A。授权 seam 是 listener 的 recipient eligibility module；subscribe validation 是防止创建无效关系的前置防线，不能替代 event-time 检查。
