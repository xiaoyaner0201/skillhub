## 4. 方案比较与冻结选择

### A（推荐并冻结）：窄 catch + 原样重抛；R8 仅增服务测试

在两处 `findById` 周围各放一个窄 catch，失败时记 ID 与 throwable，然后原样重抛；保留 `Optional.empty()` 防御分支并改为事实性 wording。R8 仅在已有参数化拒绝测试捕获 exception 并断言 `messageCode()`。

优点：闭合真实 namespace read failure，保留异步失败和零 partial sink；R8 只外溢一个测试文件，不引入生产常量/API。代价是两处相似 catch 重复，但它们是两个独立事件入口，重复比扩大 helper seam 更诚实。

### B：全局 `AsyncUncaughtExceptionHandler`

能统一异常记录，却拿不到稳定的 skill/namespace 语义参数，扩大配置/全异步面，还会改变其他 listener 的 failure observability。拒绝。

### C：捕获后返回/吞异常，或把 lookup+eligibility+dispatch 放进大 catch

返回会把真实失败伪装成正常完成；大 catch 会把 eligibility、JSON、dispatcher 失败误报成 namespace load failure。均违反 fail-closed 证据与故障归因。拒绝。

### D：R8 提取生产常量供 bundle test 引用

绑定更紧，但要求修改生产 domain service 并新增跨模块共享符号。一个 test-gap 不值得增加生产 surface。拒绝。

## 8. Council nomination

1. `trust-boundary` — **Bruce Schneier-style**：核查 repository-exception WARN、retained PRIVATE readback 与 search static surface 三个信任边界。必须回答：WARN 是否只有对象 ID、没有 candidate identity；removed/cross-ns 是否在 row/SSE 均为 0；`/me/subscriptions` 是否仍是活的 PRIVATE 数据旁路；search query sink 是否仍拒绝 PRIVATE。非 dissent。

3. `evidence-dissent` — **Kent Beck-style**：核查真实 bundle+production messageCode 双哨兵、exception RED、跨 tree tuple 与最终 row/SSE。必须回答：任一 key 侧漂移是否会 RED；WARN probe 是否断言 logger/ID/PII/throwable identity/0 sink；tuple 是否逐元素；**本方案在什么条件下是错的，以及哪些 probe 即使全绿也仍无法关闭 R1/R3/R4**。承担 dissent。
