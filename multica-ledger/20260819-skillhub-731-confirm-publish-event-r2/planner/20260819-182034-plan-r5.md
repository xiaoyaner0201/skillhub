# Composite read policy 下的 publish / yank subscriber 授权计划（plan-r5）

本计划 supersede `planner/20260819-173745-plan-r4.md`，但不改写 r4。相对 r4：**撤回**“`VisibilityChecker` 是一般 current-read 唯一合同”；**新增** account active、namespace lifecycle、skill lifecycle、hidden/publication/visibility、current namespace membership 组成的 composite read decision；**删除** platform role/SUPER_ADMIN 对普通读、通知、subscription 的穿透；**深化** R4 的 `YANKED_PUBLICATION` purpose 和最小 pre-yank publication context，使它成为 composite policy 的 publication-purpose 输入，而不是绕开其它 gates；**补齐** subscription GET/DELETE 的 source-backed语义、account batch driver、完整 reachability/invariant/RED-GREEN/QA/Reviewer范围。

原因是 pinned source 已证明：普通读资格来自 `AuthContextFilter` 与 `SkillQueryService.assertPublishedAccessible`/`VisibilityChecker` 的组合，而非单个 checker。r1-r4、旧 QA/Reviewer PASS与所有退回决定均保留为 append-only历史，不授权R5实现或发布。

## 1. Source Contract 分层

### 原始事实

- `AuthContextFilter` 对受保护portal路径先用 `UserAccountRepository.findById` 检查账号；缺失或 `!isActive()` 时清认证并返回401，后续controller/service不执行。subscriber async listener不经过该filter。
- `SkillQueryService.assertPublishedAccessible` 的生产读组合依次包含：archived namespace非当前member拒绝；`skill.status != ACTIVE`非owner/namespace ADMIN/OWNER拒绝；hidden非owner/admin拒绝；再调用 `VisibilityChecker` 处理publication/visibility/current membership。
- `VisibilityChecker` 本身仅覆盖 hidden、`latestVersionId==null`、PUBLIC/NAMESPACE_ONLY/PRIVATE及owner/namespace role；它不是完整read contract。
- `SkillQueryService#getSkillDetail(..., platformRoles)`忽略platformRoles并委托无platformRoles overload；`docs/05-business-flows.md`明确SKILL_ADMIN/SUPER_ADMIN普通读与普通登录用户一致，不自动穿透PRIVATE/hidden/unpublished。
- subscription PUT/DELETE/GET目前都只`ensureSkillExists`；PUT建关系，DELETE删自己的关系，GET只返回caller自己的relationship boolean。GET不返回skill metadata，但当前三者都经过AuthContextFilter，因此inactive caller到不了service。
- R4已正确证明yank fallback/no-fallback：no-fallback post-state latest=null不能直接代表被yank version从未发布，需要可信pre-yank publication context。

### 明确要求

- publish/yank recipient和subscription PUT必须与production portal read的composite authorization等价，且不静默新增platform-role权限。
- composite决策顺序与事实源：
  1. account存在且ACTIVE（`UserAccountRepository`）；
  2. namespace authoritative aggregate/status（`NamespaceRepository`）；
  3. skill authoritative aggregate/status（`SkillRepository`）；
  4. hidden/publication-purpose/visibility（共享policy内核）；
  5. event/request-time fresh namespace membership roles（`NamespaceMemberRepository`）。
- 任一事实缺失、查询异常或context无效均fail-closed；fan-out必须在首个dispatch前完成全批资格计算，0 partial sink。
- platform roles不参与普通read eligibility。若未来要让SUPER_ADMIN穿透，必须有独立maintainer Source Contract/decision与单独plan，不得在#731通知修复中夹带。

### Repository Invariants

- active account是所有authenticated portal操作的前置条件；通知向inactive/missing account持久化可识别metadata违反同一revocation边界。
- namespace ARCHIVED：production read仅current namespace member可继续；removed/nonmember即使skill PUBLIC也拒绝。
- skill status非ACTIVE（含HIDDEN/ARCHIVED enum状态）：仅skill owner或current namespace ADMIN/OWNER可继续；随后仍需通过hidden/publication/visibility gate。
- `hidden=true`：仅owner或current ADMIN/OWNER；platform-only SUPER_ADMIN不是namespace admin。
- current-read publication：latest=null仅owner可读；yank-publication：producer可信证明目标pre-state PUBLISHED时，latest=null shortcut不适用，但account/namespace/skill/hidden/visibility/current-membership gates全部仍适用。
- subscription关系是caller自身的社交状态，不是读取授权。PUT需授权才能创建/保留；DELETE必须可清理stale relation；GET只回答“我是否订阅”，不泄露skill metadata，不因current-read失败而隐藏自身关系。

### 合理推导与 Plan Hypothesis

- 推荐抽取domain-level `SkillReadAccessPolicy`（名称可按仓库风格微调）作为composite policy唯一正本，由生产`SkillQueryService`和app eligibility/PUT共同调用。policy输入已加载的`Namespace`、`Skill`、viewer account state、fresh namespace roles及`ReadPurpose`；返回boolean/decision，调用者将拒绝映射为既有异常或过滤。
- `VisibilityChecker`可成为policy内部实现细节或被合并进policy；不得再由listener另拼account/status/checker。现有public `VisibilityChecker`若需兼容保留，应委托共享内核，避免双规则漂移。
- `ReadPurpose.CURRENT_READ`保持production read publication语义；`ReadPurpose.YANKED_PUBLICATION(preYankPublished=true)`仅改变publication-state子判据，其余composite gates相同。
- eligibility module对一个skill fan-out：一次读取Namespace；一次`UserAccountRepository.findByIdIn(distinctCandidateIds)`；一次`NamespaceMemberRepository.findByNamespaceIdAndUserIdIn`；不查询platform roles。missing/inactive accounts不合格。所有结果完整物化后再循环dispatch。
- subscription PUT位于AuthContextFilter之后，账号active由真实entry保证；service/policy仍接受明确account-active context或authoritative account以便非HTTP caller不绕过。GET/DELETE继续依赖filter active gate，但不加current-read policy。

### 待实现前核验的有限假设

- `SkillQueryService`所有本次声称等价的portal published reads最终可迁移到同一policy而不改变错误码；若存在不同read contract，必须列出并选择明确entry，而非全局替换。
- `UserAccountRepository.findByIdIn`已存在并可单次批量读取；missing IDs可机械视为inactive/deny。
- namespace可由skill.namespaceId单次authoritative读取；缺失为fail-closed。

### Non-goals

- 不扩展platform角色普通read权限；不改变账号、namespace或skill lifecycle；不自动删除stale subscriptions。
- 不改变subscription GET返回内容或DELETE清理语义；不改notification payload、preference、yank状态/审计、search策略、outbox/retry。
- R4允许的最小yank publication context仍在范围；禁止event携带recipients/account/membership/role snapshot。
- 本阶段不修改生产/测试代码，不创建PR，不force-push/merge/close/release。

## 2. 当前 composite read decision 与失败语义

```text
authenticated production read request
→ AuthContextFilter
   → account missing/inactive: 401, no controller/service side effects
   → active: userId + current namespace roles projected
→ SkillQueryService
   → load authoritative Namespace + Skill
   → namespace ARCHIVED && !current member: forbidden
   → skill.status != ACTIVE && !owner/admin: forbidden
   → hidden && !owner/admin: forbidden
   → current publication/visibility:
      latest=null: owner only
      PUBLIC: allow
      NAMESPACE_ONLY: current member
      PRIVATE: owner or current ADMIN/OWNER
→ allowed read
```

Platform roles不进入上述判定。repository missing/error、role conversion error一律不得默认为allow。

## 3. Change Reachability Graph

### 普通读与subscription public entries

```text
GET skill detail/other published portal read
→ AuthContextFilter(account active)
→ SkillQueryService
→ [R5 shared SkillReadAccessPolicy(CURRENT_READ)]
→ response/projection

PUT /api/{v1|web}/skills/{skillId}/subscription
→ AuthContextFilter(account active + fresh memberships)
→ SkillSubscriptionController → SkillSubscriptionService
→ load Skill + Namespace
→ shared policy(CURRENT_READ; no platform-role override)
→ authorized only: relation save → counter → SkillSubscribedEvent

GET subscription
→ AuthContextFilter(active)
→ ensure skill exists → caller-owned relationship boolean
→ no skill metadata/current-read gate (source-compatible)

DELETE subscription
→ AuthContextFilter(active)
→ ensure skill exists → delete caller-owned stale/current relation
→ counter decrement → SkillUnsubscribedEvent
→ no current-read gate, so cleanup remains possible
```

### Publish subscribers

```text
confirm-publish → SkillPublishedEvent
→ subscriber listener → load authoritative Skill + Namespace
→ subscription candidates
→ batch accounts + batch current memberships
→ shared policy(CURRENT_READ) per candidate
→ eligible active recipients only; exclude publisher
→ SUBSCRIPTION_NEW_VERSION
→ NotificationDispatcher → preference → Notification save → SSE
```

### Yank fallback/no-fallback

```text
yank producer: verify target PUBLISHED → capture minimal pre-yank context
→ save YANKED → latest=fallbackId OR null → audit
→ SkillVersionYankedEvent(..., preYankPublished=true)
→ AFTER_COMMIT subscriber listener
→ load authoritative post-state Skill + Namespace
→ subscription candidates → batch accounts + memberships
→ shared policy(YANKED_PUBLICATION context)
   → account / namespace / skill status / hidden / visibility unchanged
   → publication subgate treats verified yanked version as formerly published
→ exclude actor → SUBSCRIPTION_VERSION_YANKED
→ Dispatcher → preference → Notification save → SSE
```

新/变更drivers与consumers：account batch、namespace single read、membership batch、shared policy被production read/query、PUT、publish listener、yank listener消费；最终sinks为subscription relation/counter/event与两类Notification persistence/SSE。

## 4. 方案比较与冻结选择

### 方案A（推荐）：抽取共享 composite `SkillReadAccessPolicy`

把`SkillQueryService.assertPublishedAccessible`现有namespace/skill/hidden/visibility逻辑与publication-purpose统一到domain policy；生产read entry、subscription PUT、subscriber eligibility调用同一decision。AuthContextFilter仍负责HTTP account gate，async eligibility用batch account facts补齐等价前置条件。platform roles不进入policy。

优点：production entry与新consumers共享一套规则，可由同一contract tests机械证明；account gate在各执行模型中有明确adapter；R4 purpose仅影响publication子判据；无N+1/静默扩权。代价：写集包含现有query service与domain tests，需要严格回归错误映射。

### 方案B：listener/PUT各自拼account+namespace status+skill status+VisibilityChecker

改动看似局部，但复制`assertPublishedAccessible`、hidden和management判定；未来production read变化会再次漂移，且无法机械证明等价。拒绝。

### 方案C：从HTTP skill detail内部调用/模拟controller读取来判每个recipient

表面复用production path，实际引入request context、每recipient N+1、异常/DTO副作用耦合，async listener也无法安全伪造认证。拒绝。

冻结A。共享的是纯domain authorization decision；HTTP filter与batch listener分别提供authoritative account事实。
