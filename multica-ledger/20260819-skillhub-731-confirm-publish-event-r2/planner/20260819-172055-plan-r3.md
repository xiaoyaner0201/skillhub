# confirmPublish 与 yank subscriber 授权安全计划（plan-r3）

本计划 supersede `planner/20260819-163725-plan-r2.md`，但不改写 r2。相对 r2：**新增** `SkillVersionYankedEvent → onSkillVersionYankedForSubscribers → NotificationDispatcher → persistence/SSE` 的完整授权面、RED/GREEN、QA 与 Reviewer 输入；**修改**共享 eligibility seam 的调用者从 publish 单路径变为 publish+yank 双路径，并把 yank 从 non-goal/兼容不改项改为“仅 recipient eligibility 改变”；**删除**“yank fan-out 不在范围内”这一错误边界。原因是 Plan Gate 已由源码确认 yank 使用同一陈旧 subscription、暴露同类 PRIVATE 元数据，构成 `PLAN_GAP` 关联 `INVARIANT_VIOLATION`。r1、r2、旧 QA/Reviewer PASS 与退回决定均只保留为历史，不能授权 R3 实现或发布。

## 1. Source Contract 分层

### 原始事实

- 上游目标要求 `confirmPublish` 成功后发布既有 `SkillPublishedEvent(skillId, versionId, publisherId)`；当前候选已在 version 与 skill save 成功后发布，失败时事务回滚且 0 event。
- pinned source commit `d3e49707f3960cdf8e7b20c443aeebbb056581fa`、tree `79ca7776d7d3b01fafc19e1153a19dacdcd762c0` 上，`NotificationEventListener` 的 publish 与 yank subscriber listeners 都调用 `SkillSubscriptionService.findSubscribersBySkillId`，均未做事件时授权。
- `SkillGovernanceService.yankVersion` 在 version 标记 YANKED、必要时重算 latest、写审计后发布 `SkillVersionYankedEvent(skillId, versionId, actorUserId)`；它是当前生产入口，不是未来假设。
- 两个 subscriber payload 都经 `bodyWithSkill` 与 `versionLabel` 暴露 `skillId`、display name、slug、namespace、version，并调用同一 `NotificationDispatcher`；dispatcher 先查 preference，再持久化 Notification，最后 SSE。
- `SkillSubscriptionService.subscribe` 目前只验证 skill 存在，不验证 caller 对 PRIVATE/NAMESPACE_ONLY/hidden/unpublished skill 的读取权。

### 明确要求

- 历史 subscription 只表示过去建立的关系，不授予 publish 或 yank 事件时的当前读取权。
- publish 与 yank 两条 subscriber fan-out 必须复用**同一个**批量 `SubscriptionRecipientEligibility`，逐 recipient 复用现有 `VisibilityChecker.canAccess` 合同；授权依赖失败必须在任何 dispatch 前整批 fail-closed。
- yank 事件类型 `SUBSCRIPTION_VERSION_YANKED`、title/body、actor 排除、领域状态变化、审计和 producer 事务语义保持；变化仅限最终 recipient 资格。
- 订阅 public entry 在关系写入前也必须复用读取合同；入口校验是前置防线，不能替代两条 listener 的事件时校验。

### Repository Invariants（上位事实）

- `VisibilityChecker.canAccess` 是现有 skill 读取合同：SUPER_ADMIN 始终可读；hidden 仅 owner 或 namespace ADMIN/OWNER；未发布仅 owner；PUBLIC 任意用户；NAMESPACE_ONLY 当前 namespace member；PRIVATE 仅 owner、namespace ADMIN/OWNER 或 SUPER_ADMIN。
- membership、platform-role、namespace 必须以事件处理时的 fresh records 为准；removed、left、ADMIN→MEMBER 与 cross-namespace 身份不能被 stale subscription 覆盖。
- recipient eligibility 必须在最终 fan-out sink 前封口；同一 authorization invariant 的事件不能因 producer 不同而出现分叉规则。
- listener 为 async `@TransactionalEventListener`（默认 AFTER_COMMIT）：listener 失败不能回滚已经完成的 publish/yank producer 事务。任何批量授权查询失败必须发生在第一个 dispatcher 调用前，避免 partial fan-out。
- preference disabled 时 0 persistence/SSE；notification save 失败时 0 SSE；save 成功而 SSE 失败时已持久化 notification 保留。这些 dispatcher 语义不变。

### 合理推导与 Plan Hypothesis

- 最小且系统正确的 seam 是 app listener 邻接的共享 eligibility module：输入已加载的 `Skill` 与 candidate user IDs，批量获取该 skill namespace 的 memberships 和 candidates 的 platform roles，逐人调用 checker，返回 eligible IDs。两个 listener 只对返回集合做原有 publisher/actor 去重后 dispatch。
- 为避免 N+1，membership 必须由 `namespaceId + userIds` 一次查询，platform role binding 必须由 `userIds` 一次查询；candidate 先 distinct，并在授权前完整物化两批结果。
- 入口 `subscribe` 应接收 request filter 提供的 namespace roles 与 principal platform roles，在幂等返回前重新验证 current access；否则已有 stale relation 的重复 PUT 会绕过当前拒绝语义。
- R3 不自动删除 stale subscription。保留关系与拒绝通知并不矛盾：关系是历史状态，eligibility 是事件时状态。

### 待 Coder 首先核验的假设

- `NamespaceMemberJpaRepository` 可通过 domain contract 新增 `findByNamespaceIdAndUserIdIn` 派生查询；`UserRoleBindingRepository.findByUserIdIn` 已存在且 app module 可注入。
- 两个 listener 在单次调用中均能先完成 eligibility 计算再进入 loop；若实际存在流式/分段 dispatch 或异步二次桥，需报 `PLAN_GAP`。
- `VisibilityChecker` 对 yank 后 skill 仍使用 `latestVersionId` 判断发布性；若 yank latest 后变为 null 导致 owner-only，而产品合同要求按被 yank 版本发布前可见性通知，则这是需人类决定的新合同冲突，不由 Coder猜测。

### Non-goals

- 不改 event records、producer 领域状态机、yank 审计、通知文案/body schema、preference、outbox/retry、搜索可见性或自动清除 subscriptions。
- 不把 authorization/privacy、yank recipient eligibility 或最终 notification sink 写成 non-goal。
- 本阶段不写生产/测试代码，不创建 PR，不 force-push/merge/close/release。

## 2. 当前行为与 Change Reachability Graph

### Publish producer 与全部 consumers

```text
POST /api/{v1|web}/skills/{namespace}/{slug}/confirm-publish
→ SkillLifecycleController
→ GovernanceWorkflowAppService → SkillLifecycleAppService
→ SkillReviewSubmitService.confirmPublish
→ validate → save PUBLISHED version → save skill latestVersionId
→ SkillPublishedEvent
  ├─ onSkillPublished (publisher)
  │  → NotificationDispatcher → preference → Notification save → SSE
  ├─ onSkillPublishedForSubscribers
  │  → findSubscribersBySkillId → distinct candidates
  │  → [R3 shared batched current-access eligibility]
  │  → exclude publisher → SUBSCRIPTION_NEW_VERSION
  │  → NotificationDispatcher → preference → Notification save → SSE
  └─ SearchIndexEventListener.onSkillPublished
     → rebuildBySkill → skill_search_document → query-time visibility filter
```

### Yank public entry、producer 与 subscriber sink

```text
POST /api/admin/skills/versions/{versionId}/yank
→ AdminSkillController (authenticated admin gate)
→ SkillGovernanceService.yankVersion
→ load PUBLISHED version → save YANKED/downloadReady=false
→ if latest: recompute/save skill.latestVersionId
→ auditLogService.record
→ SkillVersionYankedEvent(skillId, versionId, actorUserId)
→ NotificationEventListener.onSkillVersionYankedForSubscribers
→ skillRepository.findById
→ findSubscribersBySkillId → distinct candidates
→ [R3 same batched current-access eligibility]
→ exclude actor → SUBSCRIPTION_VERSION_YANKED
→ NotificationDispatcher
→ preference → Notification save → SSE recipient-visible payload
```

当前旧行为在 eligibility 节点完全缺失。两条路径的新可达查询/driver 为 namespace membership batch 与 platform-role batch；最终派生记录分别为 recipient 的 `SUBSCRIPTION_NEW_VERSION` / `SUBSCRIPTION_VERSION_YANKED` Notification，payload 都含可识别 skill/version 元数据。

### Subscription public entry

```text
PUT /api/{v1|web}/skills/{skillId}/subscription
→ SkillSubscriptionController
→ principal.userId/platformRoles + request.userNsRoles
→ SkillSubscriptionService.subscribe
→ load Skill → VisibilityChecker.canAccess
→ authorized: relationship lookup/save → counter increment → SkillSubscribedEvent
→ unauthorized/failure: exception, transaction rollback, 0 mutation/event
```

GET 仍只读 caller 自己的 relationship；DELETE 仍允许 caller 清理 stale relationship，不增加读取授权门槛。

## 4. 方案比较与冻结选择

### 方案 A（推荐）：共享 listener-adjacent 批量 eligibility + 入口同合同

新增 `SubscriptionRecipientEligibility.filterEligible(Skill, Collection<String>)`，批量读取 current membership/platform roles并调用唯一 `VisibilityChecker`。publish 和 yank subscriber listeners 都在构造并派发 recipient-visible notification 前调用；subscribe PUT 在保存前直接使用同一 checker 合同。

优点：在两条最终 sink 前统一封闭 stale relationship；规则只有一个正本；批量查询避免 N+1；依赖异常可在任何 dispatch 前整批 fail-closed。代价：写集横跨 app/domain/infra/auth-facing repository，必须验证真实 query 参数、两条 listener 与最终 sink。

### 方案 B：repository SQL join 直接返回 eligible subscribers

优点是单 SQL。缺点是把 PUBLIC/NAMESPACE_ONLY/PRIVATE/hidden/unpublished/SUPER_ADMIN 规则复制到查询层，形成第二授权正本，且 publish/yank/入口容易再次漂移；拒绝。

### 方案 C：只在 subscribe 时校验或只修 publish

改动最少，但撤权后关系立即陈旧；只修 publish 则 yank 继续从同一关系泄漏同类 payload，已被 source-first 证伪；拒绝。

冻结方案 A。filter seam 位于 subscriber lookup 与 dispatcher 之间；publisher/actor 排除可在 filter 后保持原行为，但所有授权查询必须在任何 dispatch 前完成。

## 8. Falsification / PLAN_GAP 条件
