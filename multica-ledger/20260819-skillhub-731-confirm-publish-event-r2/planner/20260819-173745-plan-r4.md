# confirmPublish 与 purpose-aware yank subscriber 授权计划（plan-r4）

本计划 supersede `planner/20260819-172055-plan-r3.md`，但不改写 r3。相对 r3：**新增** yank 前“曾发布且本次正在撤回”的最小 publication context，并把 yank 分成“仍有 fallback published version”与“最后一个 published version”两种状态；**修改** eligibility API，从对 current `Skill` 一刀切的过滤改为显式 `CURRENT_READ` / `YANKED_PUBLICATION` purpose；**允许并要求**扩展 `SkillVersionYankedEvent`，传递非 recipient、非 role 的 pre-yank publication marker；**保留** publish subscriber、subscription PUT、批量 fresh role 查询、fail-closed 与最终 sink 建模。原因是 pinned source 已证明：最后一个 published version 被 yank 后 current `Skill.latestVersionId=null`，直接调用现有 `VisibilityChecker.canAccess` 会误套“从未发布/当前无发布版本”语义，破坏 yank compatibility control case。

r1、r2、r3、旧 QA/Reviewer PASS 及两次退回决定均为 append-only 历史，不授权 R4 实现或发布。

## 1. Source Contract：事实、要求、推导、假设、non-goals

### 原始事实

- `SkillGovernanceService.yankVersion` 先把目标 version 从 PUBLISHED 改为 YANKED；若目标是 latest，则查询剩余 PUBLISHED versions 并把 `skill.latestVersionId` 改为 fallback id 或 `null`；随后写审计并发布 `SkillVersionYankedEvent(skillId, versionId, actorUserId)`。
- async AFTER_COMMIT listener 重新读取的是变更后的 Skill。`VisibilityChecker.canAccess` 在 visibility switch 前检查 `latestVersionId == null`，除 SUPER_ADMIN 外仅允许 owner。
- 所以最后一个 published version 的 PUBLIC 普通 subscriber、NAMESPACE_ONLY 当前 MEMBER、PRIVATE 当前 ADMIN/OWNER，如果直接用 current Skill `canAccess`，都会被错误拒绝；这与 GitHub #731 的“yank 后 subscribers 收到通知”control case和既有 yank fan-out兼容合同冲突。
- publish 与 yank subscriber listeners 当前都从同一 stale-capable subscription relation 取 candidates，并通过同一 dispatcher 暴露 `skillId/name/slug/namespace/version`，当前均无事件时授权。

### 明确要求

- publish notification 与 subscription PUT 使用**当前读取**语义：直接复用 `VisibilityChecker.canAccess(current Skill, fresh roles)`。
- yank notification 使用**被撤回 publication 的通知资格**语义：目标 version 在 producer 事务开始时已确认 PUBLISHED；listener 必须基于 skill 的 visibility/hidden/owner与事件处理时 fresh membership/platform roles判定，不能把 yank 后 `latestVersionId=null` 误解释为“从未发布”。
- yank 有 fallback 与无 fallback 两种状态都要保持合法 subscriber control case；removed、downgraded、cross-namespace 等失权 recipient 两种状态都必须拒绝。
- recipient list 与 role snapshot不得固化进 producer/event；fresh roles必须在 listener 批量查询，授权依赖失败在首个 dispatch 前整批 fail-closed。

### Repository Invariants

- `VisibilityChecker` 是一般 skill current-read 的唯一合同。它的 `latestVersionId==null → owner only` 对普通读取正确，不应为通知特例而全局放宽。
- yank 是一个 purpose-specific authorization decision：对象是“刚刚从 PUBLISHED 撤回、需要通知既有 subscriber 的 version”，而非“当前是否存在可读取 published version”。该事实必须由 producer可信地产生，不能由 listener仅看 post-state猜测。
- purpose-aware 判定仍必须复用同一 visibility/hidden/owner/namespace-role/platform-role规则实现；不得复制一个未来会漂移的 switch。
- event只能携带稳定、最小的领域事实，不能携带 recipients、membership roles或 platform roles。
- publisher/actor排除、通知文案/payload、dispatcher preference/persistence/SSE与 async AFTER_COMMIT失败边界保持。

### Plan Hypothesis 与合理推导

- 推荐在 domain `VisibilityChecker` 增加显式 purpose/context，而非新增第二 checker：
  - `CURRENT_READ`：保持现有 `canAccess` 全部语义；publish与subscribe调用此路径。
  - `YANKED_PUBLICATION`：要求可信 context `wasPublishedBeforeYank=true`，保留 SUPER_ADMIN、hidden、visibility、owner和fresh role规则，但跳过 post-state `latestVersionId==null` 的 unpublished shortcut。
- `SkillVersionYankedEvent` 扩展最小字段 `wasPublishedBeforeYank`（或更强类型的 publication context）。producer已在 mutation前验证 `version.status == PUBLISHED`，因此可固定传 true；字段不是权限结论，只证明 eligibility purpose的前置事实。listener不得自行把任意 event/skill标成 yank-publication。
- `SubscriptionRecipientEligibility.filterEligible(skill, candidates, accessPurpose/context)` 仍统一完成 distinct、批量 fresh membership/platform roles和逐人 checker调用；共享的是角色获取与规则内核，不强迫 publish-current与yank-pre-state共享错误的 publication-state前提。
- 若团队更偏好类型安全，event字段可用枚举/record context代替 boolean，但不得增加 recipient/role snapshot；对本计划验收语义等价。

### 已证实事实，不再作为 Coder 假设

- yank最后一个 published version后 `latestVersionId` 可为 null；这是当前 `orElse(null)` 与 AFTER_COMMIT read直接证明的可达分支。
- 此分支直接调用 current-read checker会误拒合法 PUBLIC/NAMESPACE_ONLY/PRIVATE-admin recipients；Coder不得再“核验后自行决定”。

### Non-goals

- 不全局改变 current-read 的 unpublished/hidden/visibility语义；不把 yank recipient list或roles放入event；不自动删除 stale subscriptions。
- 不改 yank领域状态、审计、actor exclusion、notification eventType/title/body、preference、outbox/retry或搜索策略。
- event record变化**不再是 non-goal**；R4明确允许上述最小 publication context。
- 本阶段不修改生产/测试代码，不创建 PR，不 force-push/merge/close/release。

## 2. 当前行为与完整 Change Reachability Graph

### Publish / subscription（保留 R3）

```text
confirm-publish → save version PUBLISHED → save skill → SkillPublishedEvent
├─ publisher listener → Dispatcher → preference → Notification save → SSE
├─ subscriber lookup → eligibility(CURRENT_READ, current Skill, fresh roles)
│  → exclude publisher → SUBSCRIPTION_NEW_VERSION → Dispatcher → save → SSE
└─ SearchIndexEventListener → rebuild → search document → query visibility

PUT subscription → principal + request fresh roles → load Skill
→ VisibilityChecker(CURRENT_READ) → relation save → counter → event
```

### Yank producer、两种 post-state 与 sink

```text
admin yank(versionId)
→ load version; require pre-state PUBLISHED
→ capture publicationContext.wasPublishedBeforeYank=true
→ save version YANKED
→ if target == latest:
   ├─ remaining PUBLISHED exists → skill.latestVersionId=fallbackId
   └─ none remains              → skill.latestVersionId=null
→ save skill if changed → audit
→ SkillVersionYankedEvent(skillId, versionId, actorUserId, publicationContext)
→ AFTER_COMMIT onSkillVersionYankedForSubscribers
→ reload post-state Skill + subscription candidates
→ eligibility(YANKED_PUBLICATION, current metadata, event context, fresh roles)
   ├─ fallback exists: same visibility-role outcome as current-read
   └─ no fallback: do NOT take current-read unpublished shortcut;
                   apply hidden/visibility/owner + fresh roles
→ exclude actor → SUBSCRIPTION_VERSION_YANKED
→ NotificationDispatcher → preference → Notification save → SSE
```

新增/变化的 producer是 event context；caller是 yank service唯一 event constructor；consumer是 yank subscriber listener；共享 query drivers仍是 namespace membership batch与platform-role batch；最终派生记录/payload不变。

## 3. 授权时点、对象与领域合同

| Purpose | 授权对象 | publication state来源 | role时点 | latest=null语义 |
|---|---|---|---|---|
| `CURRENT_READ`（publish subscriber、PUT） | 当前 Skill | listener/service读取的current Skill | 当前 fresh | 从未发布/当前无发布：owner only |
| `YANKED_PUBLICATION` | 本次刚从PUBLISHED撤回的 version通知 | producer在mutation前验证并写入event最小context | listener当前 fresh | 不代表从未发布；继续按hidden/visibility/owner判定 |

两者共享 visibility规则内核与batch role acquisition，但purpose不可互换。若 `YANKED_PUBLICATION` 缺失/false/未知context，整批fail-closed；不得回退到“猜曾发布”。

## 4. 方案比较与冻结选择

### 方案 A（推荐）：purpose-aware `VisibilityChecker` + 最小 pre-yank context

扩展现有 checker接受明确 access purpose/context；普通 `canAccess`委托 `CURRENT_READ`保持二进制/语义兼容。yank event携带 producer验证的最小 publication marker，listener仍查询fresh roles并经共享 eligibility module调用 checker。

优点：visibility/hidden/owner/SUPER_ADMIN规则仍是一个正本；正确区分 post-state 与被撤回对象；无 stale-role授权；event不携带recipient；两种yank状态结果一致且可解释。代价：event record及构造/测试写集扩大，但这是消除已知歧义的最小领域事实。

### 方案 B：专门 `YankNotificationEligibility` 在 app层重写 visibility规则

读取 current Skill metadata，忽略 latest-null并自行switch visibility。

优点：event无需变化、改动局部。缺点：复制 checker的hidden/owner/namespace/SUPER_ADMIN规则，未来current-read变化易漂移；listener仅凭post-state也不能证明目标确实pre-yank PUBLISHED。拒绝。

### 方案 C：producer计算并携带 recipient list或role snapshot

优点：listener简单，完整保存pre-state。缺点：事务内角色可能在AFTER_COMMIT消费前撤销，形成stale-role授权；event膨胀且把fan-out固化到producer。拒绝。

冻结方案A。最小event context用于证明purpose前提，fresh角色仍只在consumer侧查询；规则内核仍在一个checker中。
