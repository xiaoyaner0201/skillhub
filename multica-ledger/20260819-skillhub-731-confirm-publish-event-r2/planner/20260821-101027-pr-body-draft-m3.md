## Breaking-change disclosure and subscription data decision

`PUT /skills/{id}/subscription` now requires the caller to have current read access to the skill. A caller without that access receives HTTP 403. This is an intentional tightening of the subscription boundary.

Existing `skill_subscription` rows are not deleted automatically. Rows created by ordinary members for skills that are now `PRIVATE`, or rows whose users no longer have access to `NAMESPACE_ONLY` skills, can therefore remain in the database. The event-time eligibility check excludes those rows from subsequent subscriber notifications when the account, namespace membership, or skill visibility facts no longer authorize access.

Those retained rows are not inert. `GET /me/subscriptions` remains a live metadata readback path, and the current implementation does not apply the subscription metadata access policy before projecting a retained row into `SkillSummaryResponse`. A former subscriber can therefore continue to receive top-level skill metadata such as slug, display name, summary, namespace, and `visibility: "PRIVATE"` after a PUBLIC-to-PRIVATE change. `GET /skills/{id}/subscription` also continues to report the caller's retained relationship. The metadata readback issue is inherited from the upstream base; this targeted change neither introduced nor fixes it.

Our proposed default is to retain those rows for this PR while the data-lifecycle and readback policy are decided explicitly. Notification delivery already fails closed against current account, namespace membership, and skill visibility facts. Automatic cleanup would add irreversible writes and counter-reconciliation rules, while retaining rows leaves the existing metadata readback exposure open; neither consequence should be hidden from the decision.

Maintainer decision requested:

- [ ] Retain existing rows for this PR and handle metadata readback authorization separately.
- [ ] Add a one-time migration/prune in this PR (please confirm deletion criteria and counter reconciliation).
- [ ] Open a follow-up issue to define retention, metadata readback, counters, and cleanup semantics before pruning.
