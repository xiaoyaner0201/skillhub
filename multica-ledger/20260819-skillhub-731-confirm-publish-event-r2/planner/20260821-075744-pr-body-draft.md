## Breaking-change disclosure and subscription data decision

`PUT /skills/{id}/subscription` now requires the caller to have current read access to the skill. A caller without that access receives HTTP 403. This is an intentional tightening of the subscription boundary.

Existing `skill_subscription` rows are not deleted automatically. Rows created by ordinary members for skills that are now `PRIVATE`, or rows whose users no longer have access to `NAMESPACE_ONLY` skills, can therefore remain in the database while being excluded from subsequent subscriber notifications by the event-time eligibility check.

Our proposed default is to retain those rows for this PR. Notification delivery already fails closed against current account, namespace membership, and skill visibility facts, while automatic cleanup would introduce a data-lifecycle decision and irreversible writes beyond the targeted authorization fix.

Maintainer decision requested:

- [ ] Retain existing rows; do not add a migration or prune step.
- [ ] Add a one-time migration/prune in this PR (please confirm the intended deletion criteria).
- [ ] Open a follow-up issue to define retention, user-visible readback, counters, and cleanup semantics before pruning.
